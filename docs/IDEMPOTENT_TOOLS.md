# Идемпотентные mutation-tools

Эти инструменты предназначены для внешних систем, которые могут повторить запрос после сетевой ошибки и не имеют права создать второй документ/объект.

## Принцип

`idempotencyKey` обязан быть UUID. При создании нового справочника или документа этот UUID используется как UUID ссылки объекта через `УстановитьСсылкуНового` **до записи**.

Повтор с тем же `idempotencyKey`:

1. формирует ту же ссылку;
2. проверяет, существует ли объект с этой ссылкой;
3. если существует — возвращает уже созданный объект;
4. новый объект не создаётся.

Это делает неоднозначный сетевой retry детерминированным на стороне 1С, а не только на стороне вызывающего сервиса.

## `onec_idempotent_write_object`

Создаёт или изменяет справочник/документ. Для нового объекта также поддерживает безопасный resolve-or-create по `matchFields`.

Обязательные параметры при создании:

```json
{
  "metaType": "Documents",
  "name": "ИмяДокумента",
  "idempotencyKey": "11111111-2222-3333-4444-555555555555"
}
```

Поддерживаются:

- `metaType`: `Catalogs` / `Documents`;
- `name`;
- `idempotencyKey`;
- `uuid` — если указан, выполняется изменение существующего объекта, а не создание;
- `matchFields` — точные поля естественного ключа, используемые **только при создании** для поиска существующего объекта;
- `fields`;
- `tabularSections`;
- `replaceTabularSections`;
- `writeMode`: `save`, `post`, `unpost` для документов;
- `postingMode`: `operational`, `nonoperational`.

Для справочников разрешён только `writeMode=save`.

Поля `Ссылка`, `Проведен`, `ПометкаУдаления` нельзя устанавливать напрямую.

### `matchFields`

Если `uuid` не задан и передан непустой `matchFields`, порядок работы такой:

1. сначала проверяется deterministic replay по UUID=`idempotencyKey`;
2. затем строится точный запрос по всем полям из `matchFields`;
3. если совпадений нет — создаётся новый объект с UUID=`idempotencyKey` и применяются `fields`;
4. если найден ровно один объект — он возвращается **без записи и без изменения его полей**;
5. если найдено два или больше объектов — операция завершается ошибкой неоднозначности.

Пример для сопоставления контрагента по ИНН:

```json
{
  "metaType": "Catalogs",
  "name": "Контрагенты",
  "idempotencyKey": "11111111-2222-3333-4444-555555555555",
  "matchFields": {
    "ИНН": "1234567890"
  },
  "fields": {
    "Наименование": "ООО Клиент",
    "ИНН": "1234567890"
  },
  "writeMode": "save"
}
```

Такой вызов является resolve-or-create, а не скрытым update. Если контрагент с этим ИНН уже существует, переданные `fields` его карточку не переписывают.

## `onec_idempotent_create_on_basis`

Создаёт документ штатным механизмом `Документ.Заполнить(Основание)` и делает создание идемпотентным.

Пример:

```json
{
  "targetDocument": "ИмяДокументаНазначения",
  "basisMetaType": "Documents",
  "basisName": "ИмяДокументаОснования",
  "basisUuid": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
  "idempotencyKey": "11111111-2222-3333-4444-555555555555",
  "writeMode": "save"
}
```

Перед первым созданием документу назначения назначается ссылка с UUID=`idempotencyKey`. Повтор возвращает уже существующий документ и не запускает второе создание.

## VORQ

VORQ использует UUID своей durable integration-command как remote `idempotencyKey`. Значение вставляется VORQ после пользовательских и фиксированных аргументов, поэтому вызывающий пользователь и конфигурация connection не могут его подменить.

Для mutation-операций VORQ разрешает MCP-мэппинг только на:

```text
onec_idempotent_write_object
onec_idempotent_create_on_basis
```

Старые `onec_write_object`, `onec_create_on_basis` и другие mutation-tools остаются полезными для прямной административной работы MCP, но VORQ не использует их для автоматически повторяемых accounting-команд.

## Ограничение

Идемпотентность относится к **созданию нового объекта** по одному command UUID. Обновление существующего объекта по `uuid` не превращается в CAS/versioned-write автоматически: конкурентные бизнес-изменения должны отдельно контролироваться правилами конкретного сценария.

`matchFields` уменьшает риск дублей по естественному ключу, но не заменяет уникальное бизнес-ограничение внутри 1С, если независимые внешние клиенты одновременно создают один и тот же ключ разными командами.
